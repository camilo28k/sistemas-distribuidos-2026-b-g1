# PDR — Project Design and Responsibilities: EduTrack
**Distributed school-tracking platform for parents and guardians**

Project: Distributed Systems 2026-B — Team G1
Complementary to the EduTrack PRD
Date: August 2026
Version: 1.0 — MVP 1

## 1. Purpose of this document

This document complements the EduTrack PRD and defines how development of MVP 1 will be organized.

The main goal is to split the system into small, clear modules so each team member owns a specific responsibility and can work independently without losing overall project integration.

Each member will be responsible for one module or core functionality, including its implementation, basic tests, and documentation.

## 2. General system organization

EduTrack will be divided into five main modules:

| Module | Responsibility |
|---|---|
| Identity & Accounts | Users, parents, students and schools |
| Academic Records | Assignments and grades |
| Attendance | Attendance registration and tracking |
| Notifications | Alerts and notifications for parents |
| Communication | Messages between parents and teachers |

Each module has a specific responsibility and communicates with other modules via REST APIs or events.

This division allows the team to apply distributed systems concepts and work on different parts of the project in parallel.

## 4. Communication between modules

To keep the project simple, two main types of communication will be used.

**Synchronous communication:** REST APIs, used when a module needs an immediate response.

Example: `Parent → Dashboard → Academic Records → Query grades`

**Asynchronous communication:** Events, used when an action can be processed later.

Example: `Academic Records → GradeCreated → Notifications → Parent`
Also: `Attendance → StudentAbsent → Notifications → Parent`

This demonstrates distributed communication without adding unnecessary complexity.

## 5. Main MVP flow

One of the system's core flows is grade registration:

1. The teacher registers a grade.
2. Academic Records stores the grade.
3. The `GradeCreated` event is emitted.
4. Notifications receives the event.
5. A notification is generated for the parent.
6. The parent can view the new grade from EduTrack.

If the Notifications service is temporarily down, the grade remains stored and queryable. The notification can be processed later via a retry mechanism.

## 6. Attendance flow

To demonstrate duplicate-event handling, the absence registration flow is used:

1. The teacher registers that a student was absent.
2. Attendance stores the absence.
3. The `StudentAbsent` event is emitted.
4. Notifications receives the event.
5. The event ID is checked.
6. A notification is generated for the parent.

If the same event arrives again: `StudentAbsent → check ID → event already exists → ignore`

This demonstrates the idempotency concept within the system.

Each module keeps its own responsibility and avoids depending directly on the internal logic of the other modules.

## 8. Internal architecture

Each module will follow a simple hexagonal architecture.

Proposed structure:

```
src/
├── domain/
│   ├── entities/
│   └── events/
├── application/
│   ├── usecases/
│   └── ports/
├── adapters/
│   ├── api/
│   └── persistence/
```

- **Domain:** core entities and business rules. Must not depend directly on databases, APIs or external services.
- **Application:** use cases that coordinate domain logic.
- **Ports:** interfaces required to communicate with external elements.
- **Adapters:** implementations for REST APIs, persistence, messaging and other external technologies.

## 9. Individual responsibility

Each member must deliver, at minimum:
- Implementation of their module
- A short README explaining how it works
- Basic unit tests
- Evidence of functionality
- Commits related to their work
- The Pull Request corresponding to their user story
- Documentation of important decisions when needed

This makes each member's individual contribution clearly identifiable.

## 10. Team integration

Even though each member owns one main responsibility, all modules must respect common contracts.

Before implementing communication between modules, the team must define:
- Event or endpoint name
- Data received
- Data returned
- Event identifier
- Possible errors

Example event:

```
Event: GradeCreated

Data:
- eventId
- studentId
- subjectId
- grade
- createdAt
```

The Notifications module does not need to know how Academic Records stores a grade — it only needs to know the event contract. This reduces coupling between modules.

## 11. Git strategy

Development will use separate branches per user story.

```
main
 └─ develop
     ├─ feature/HU-001-academic-records
     ├─ feature/HU-002-notifications
     ├─ feature/HU-003-identity
     ├─ feature/HU-004-communication
     └─ feature/HU-005-attendance
```

Each member will work mainly on their own branch.

Expected flow: `feature → Pull Request → develop → tests → main`

This helps reduce conflicts and keeps individual evidence of the work done.

## 12. Testing strategy

Each owner must test their module before integrating it.

- **Unit tests:** validate the module's internal rules (e.g., "a valid grade can be registered correctly").
- **Integration tests:** verify communication with databases, messaging or other components.
- **Contract tests:** verify that events and APIs respect the structure agreed upon by the team.
- **E2E tests:** validate complete system flows (e.g., "Teacher registers absence → Attendance → Event → Notifications → Alert to parent").

## 13. Shared responsibilities

Some tasks are the responsibility of the whole team:
- Defining contracts between modules
- Reviewing Pull Requests
- Integrating the different modules
- Running E2E tests
- Keeping documentation up to date
- Resolving integration conflicts
- Preparing the final demo

## 14. MVP 1 scope

To avoid unnecessary complexity, MVP 1 will focus on:
- Basic user management
- Parent-student relationships
- Grade registration and query
- Attendance registration and query
- Grade and absence notifications
- Basic parent-teacher communication
- Event-driven communication
- Idempotency
- Retries
- Outbox for important events

Left for future versions:
- Artificial intelligence
- Academic risk prediction
- Advanced PDF reports
- Shared school calendar
- Additional features not needed to demonstrate the distributed system

## 15. Success criteria

The MVP will be considered successful when at least one complete distributed flow can be demonstrated:

`Teacher registers information → responsible module stores the data → an event is emitted → another module processes the event → the parent receives or queries the information.`

Additionally, the system must continue operating partially when one of the secondary services fails.

## 16. Expected outcome

By the end of MVP 1, EduTrack will have a simple distributed architecture in which each member has a clearly identifiable responsibility.

Dividing the system by modules allows parallel work, reduces Git conflicts, and demonstrates distributed systems concepts such as:
- Synchronous and asynchronous communication
- Eventual consistency
- Idempotency
- Events
- Retries
- Outbox
- Fault tolerance
- Separation of responsibilities

This PDR complements the EduTrack PRD by turning the product's general requirements into a technical organization and a clear division of responsibilities for the team.
